## Explanation

### Design

**Why programmatic nbconvert, not subprocess?**  The `export()` function uses
the nbconvert Python API (`HTMLExporter`, `ExecutePreprocessor`) rather than
shelling out to `jupyter nbconvert`.  The programmatic API gives clean error
propagation (ImportError → RuntimeError with an actionable message), avoids
shell quoting issues on Windows, and makes the function straightforwardly
testable.  The subprocess approach is fine for one-shot scripts but harder
to mock in unit tests.

**`allow_errors=True` in ExecutePreprocessor.**  This is the key design
choice.  If any cell raises an exception (e.g., a NameError because a
previous cell failed to define a variable), execution continues rather than
aborting.  For this notebook, which has graceful "no data" fallbacks in every
cell, this means a partial-results page always renders rather than producing
an empty or broken HTML file.  The cell errors appear as output tracebacks
(visible if show_input=True, otherwise invisible), so they don't pollute the
portfolio page.

**`embed_images=True`.**  The HTML is a single portable file.  Without this,
nbconvert writes image files to a sibling directory and references them by
relative path — broken the moment the HTML is moved.  Embedding as base64
data URIs costs ~33% in file size (362 KB vs ~270 KB linked) but the file
is self-contained and can be dropped anywhere.

**`exclude_input=True` (default).**  The portfolio viewer wants results, not
Python source.  The code is the deeper artifact — it lives in the .ipynb and
in the backtest/ modules, which are more readable than HTML-rendered source
anyway.  Laith can pass `--show-input` for a version that includes the cells.

**`find_repo_root` walk.**  The notebook needs to know the repo root at
execution time so `sys.path` is set correctly and CSV/JSON results load from
the right paths.  The walk-up pattern is the same used inside the notebook
itself (`_here`, `_root` walk in cell 1) and avoids coupling the script to
any hardcoded path.

**Syntax-highlighting caveat in tests.**  The `test_show_input_includes_code`
test originally checked for `"import matplotlib" in html`.  This fails because
nbconvert uses Pygments to syntax-highlight code: the string becomes
`<span class="kn">import</span> <span class="nn">matplotlib</span>`.  The
correct discriminator is `'nn">matplotlib'` (the Pygments Name.Namespace span
for the module name), which is present when code is shown and absent when
excluded.

### Alternatives rejected

- **Generating HTML from `nb_utils.py` directly without executing the
  notebook**: cleaner for a pure-Python build step, but would require
  reimplementing all the matplotlib charting logic outside the notebook.
  The notebook is already the canonical rendering — nbconvert is the right
  layer to produce HTML from it.

- **Storing HTML in a `results/` directory instead of `notebooks/`**: rejected
  because `results.html` is the rendered form of `results.ipynb`; co-locating
  them makes the relationship obvious.

- **Using `nbconvert --execute` CLI via subprocess**: rejected because
  subprocess makes the missing-nbconvert test awkward (you'd need to mock
  `subprocess.run` rather than `sys.modules`), and error messages from the
  CLI are harder to intercept and format cleanly.
