### `backtest/scripts/download_cache.py` — new module (100 lines)

```python
# Public interface
DOWNLOAD_SYMBOLS: list[str]   # UNIVERSE_2010 + ["SPY", "^VIX"] = 102 symbols
START  = date(2010, 1, 1)
END    = date(2024, 12, 31)

def download(symbols, start, end) -> list[str]
    """Download each symbol individually (for visible progress). Returns failed list."""

def dry_run(symbols) -> None
    """Print CACHED/missing status for each symbol without downloading."""

def main(symbols=None, is_dry_run=False) -> None
    """Orchestrate download, print progress, print next-step instructions."""
```

The script loops over symbols one-by-one rather than calling `fetch_bars(all)`
in one shot so progress is visible.  Each symbol prints `[  3/102] AAPL  ok (3521 rows)`.
Symbols with no yfinance data (expected: handful of post-2010 delistings) are
logged as FAILED and listed at the end — not treated as errors unless ALL symbols fail.
A `sys.exit(1)` fires only when 0 symbols succeed (network-blocked environment).

## Explanation

### Why the gitignore bug was silent

`git add data/cache/` on a gitignored path produces no error and no output
on most git versions — it just does nothing.  The file never appears in
`git status` either.  A developer following the previous journal's instructions
would have run the add command, seen no error, tried to commit, and seen
"nothing to commit" — leaving them confused about why the parquet files weren't
tracking.  The fix is simply to remove the overly broad exclusion rule.

### Why this unblocks 3.1 cleanly

The full unblock workflow is now:

```bash
# On any machine with unrestricted internet access (Laith's laptop, etc.)
cd meridian/
python -m backtest.scripts.download_cache       # ~5-15 min

# Commit the 102 parquet files (~180 MB total)
git add data/cache/
git commit -m "add yfinance parquet cache (2010-2024)"
git push origin main
```

The next cloud routine session finds the parquet files via `_cache_covers()`,
skips all network downloads, and runs the quant backtest end-to-end.
`run_quant.py` is already fully implemented and tested.

### Why the download script downloads one symbol at a time

`fetch_bars()` already implements per-symbol download + caching in its loop.
The download script could call `fetch_bars(ALL_102_SYMBOLS, START, END)` in
one shot, which would work correctly.  The reason to loop one-at-a-time instead
is **progress visibility**: a single 102-symbol call runs silently for 15 minutes
with no output, which is frustrating when you can't tell if it's working.
Per-symbol output (`[3/102] AAPL  ok (3521 rows)`) gives immediate feedback
and makes partial-failure cases obvious without needing a log file.

### Why not fetch_bars batching

Batching (e.g., 10 at a time) would complicate both the script and the progress
display without providing meaningful throughput improvement — yfinance's rate-limit
pause is per-symbol regardless.
