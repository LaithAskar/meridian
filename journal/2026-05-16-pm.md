## Explanation

### Design

**Three orthogonal questions.** Each check targets a specific failure mode:

| Check | Question | What it rules out |
|---|---|---|
| `parameter_sensitivity` | Is Sharpe stable as `max_positions` varies? | Overfit to one specific parameter value |
| `walk_forward` | Is the edge consistent across consecutive periods? | One lucky stretch driving the full-window Sharpe |
| `monte_carlo_trades` | Is the edge spread across many trades, or from a few outliers? | A handful of outsized wins inflating the signal |

**`_run_engine` isolation.** All three checks ultimately call the QuantStrategy + Engine. Rather than monkeypatching deep into Engine or fetch_bars (which pulls the network in), I isolated the engine invocation into a single module-level function `_run_engine`. Tests replace this one function. This pattern also means callers (parameter_sensitivity, walk_forward) never need to know about the Engine's internal shape.

**`parameter_sensitivity` design.** Takes `positions_grid: list[int] | None` with a sensible default `[5, 10, 15, 20]`. Returns a DataFrame indexed by `max_positions` — the natural shape for a sensitivity table. Callers pass pre-fetched `spy_close` / `vix_close` so the grid loop doesn't re-fetch SPY/VIX on every call; this matters when the caller has already fetched those series for the main run.

**`walk_forward` design.** `_split_folds` divides `[start, end]` into `n` approximately equal consecutive windows; the last fold absorbs any remainder so the full date range is always covered. Each fold runs with `initial_cash` *reset* — this makes fold Sharpes directly comparable regardless of P&L in prior folds. Without resetting cash, a bad fold leaves less capital for the next and the Sharpe comparison becomes apples-to-oranges.

Because the quant strategy uses no fitted parameters (momentum windows, RSI thresholds, Bollinger Band periods are fixed constants, not optimized), each fold is a true out-of-sample evaluation — there is nothing to leak from prior folds. The walk-forward is therefore a time-period consistency check, not an expanding-window optimization.

**`monte_carlo_trades` design.** This required careful thought. Shuffling daily returns (without replacement) is invariant to permutation for Sharpe (mean and std don't change). Bootstrapping with replacement does change mean and std, giving a genuine bootstrap distribution for the Sharpe estimate.

The unit of resampling is the trade, not the day, which directly answers the interview question: "what if a different subset of these trades had occurred?" Per-trade return is computed as `pnl / (entry_price × qty)` — normalised for position size so each trade is a comparable observation regardless of notional size. Annualisation uses `sqrt(n_trades / years)` so the trade-level Sharpe is on the same scale as the daily-bar Sharpe.

The one-sided p-value is `P(bootstrap Sharpe ≤ 0)`: the fraction of resamples that flip to a non-positive edge. Low p-value (< 5%) means the edge is robust across trade samples; high p-value means it depends on specific outlier trades.

### Alternatives rejected

- **Permutation test (without-replacement shuffle) instead of bootstrap**: rejected because permuting trade returns is invariant to Sharpe by definition — the test would always give p_value = 0 or be meaningless. Bootstrap with replacement is the correct tool.
- **Daily return bootstrap instead of trade-level**: rejected for this check — the TODO specified "trade ordering" and the trade-level bootstrap directly answers the outlier-trade question. The daily bootstrap would conflate signal edge with day-to-day volatility.
- **Walk-forward with parameter tuning (train → tune `max_positions` → test)**: rejected because there is nothing to tune in this strategy. Implementing a fake tuning step would misrepresent the methodology. The honest framing is "time-period consistency."
- **Writing robustness results to disk automatically**: rejected — the robustness functions return DataFrames / dicts; the caller (run_quant.py or notebook) decides what to save. Keeping I/O out of the functions makes them testable and composable.
