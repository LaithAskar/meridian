## Explanation

### Design

The benchmark comparison lives in three layers:

**Layer 1 — pure computation (`metrics.py`):**  
`excess_sharpe(returns, benchmark_returns)` is a one-liner (`sharpe(strat) − sharpe(bench)`) but isolating it in metrics.py makes it independently testable and signals its mathematical status: it's a single number derived from two other numbers, not a join or a table lookup.

`benchmark_metrics(price_series, years)` takes raw closing prices (not returns) and computes the four things a buy-and-hold can report. It intentionally does NOT return trade-based metrics — doing so would require synthesising phantom "entry" and "exit" events, which would obscure the methodology. The design choice is explicit absence rather than silent NaN: callers see `{"sharpe": 0.82, "max_drawdown": 0.34, "total_return": 3.15, "cagr": 0.103}` and know what they're getting.

**Layer 2 — orchestration (`run_quant.py`):**  
Three `_spy_*` module-level helpers keep `run_quant_backtest` readable. `_spy_slice` uses boolean indexing (not `.loc[start:end]` on a DatetimeIndex) because boolean masks are unambiguous when the SPY series may have gaps or non-monotonic dates from the yfinance cache.

`excess_sharpe` is injected into each window's metrics dict, always keyed under `"excess_sharpe"`, always `None` when SPY data is absent. The `"benchmark"` top-level key mirrors the `"full_window"` / `"pre_covid"` / `"post_covid"` structure so the notebook can iterate over windows uniformly.

**Layer 3 — display (`nb_utils.py`):**  
`build_metrics_comparison` treats SPY B&H as a column, not a row — consistent with its existing pattern of one column per strategy. The `BENCHMARK_METRIC_KEYS` constant makes it explicit which metrics are valid for a passive benchmark; callers do not need to know the internal logic.

`regime_sharpe_df` adds a `"SPY B&H"` row when a benchmark is provided. The Sharpe-per-regime table is the canonical interview exhibit: "here is the strategy Sharpe in each regime, and here is SPY's Sharpe as context." Both functions have `benchmark=None` as default, so all existing callers and tests are unaffected.

### Alternatives rejected

- **Storing excess_sharpe in a separate file**: rejected — embedding it in the existing metrics dict keeps the data model simple and ensures excess_sharpe is always in sync with the strategy Sharpe it annotates.
- **Computing excess Sharpe at the notebook layer**: rejected — metrics.json should be self-contained. A reader of the JSON should see everything needed for the exhibit without recomputing.
- **Including SPY trade-based metrics (synthesised as one giant "trade")**: rejected — misleading, non-standard, and would confuse hit_rate / avg_win interpretations.
